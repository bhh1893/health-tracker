# CI/CD and image registry: CI builds and pushes to GHCR, Argo CD pulls from git, hooks run migrations and the smoke test

GitHub Actions builds an image per changed service and pushes it to a public GHCR package tagged with the commit SHA. A bot commit writes that SHA into the Kustomize overlay, and Argo CD, running in the cluster, notices the commit and deploys it: a migration Job first, then `api` and `web`, then a smoke test. Nothing outside the cluster holds cluster credentials ([CI/CD and image registry](https://github.com/bhh1893/health-tracker/issues/35)).

The constraint that shaped it: GitHub-hosted runners cannot reach `192.168.x.x`, so CI cannot deploy to the cluster, and a registry on the dev VM or in the cluster would be unreachable to CI. The cluster must pull.

## Shape

- **Trigger:** every merge to `main` that passes `ci-gate` (ADR 0014) deploys. Path filters (ADR 0003) mean only a changed service is built. No release tags, no `latest`.
- **Registry:** GHCR, **public** packages `ghcr.io/bhh1893/health-tracker-<svc>:<sha>`. Nodes pull anonymously, so there is no pull Secret and no entry for one in ADR 0015's inventory. The image carries the `org.opencontainers.image.source` label, which links the package to the repo. A package from a private repo starts private; flip it to public once in the package settings (check at build whether this can be reversed; treat it as permanent). Images never contain secrets (ADR 0015).
- **Image build:** PRs run `docker build` without push (ADR 0014). On merge, `docker/build-push-action` builds `linux/amd64` only, with the GitHub Actions layer cache. Base images are pinned to an exact tag; bumping is a manual PR. No vulnerability scanning, signing or tag pruning in v1.
- **Tag into git:** after the push, a CI job commits the new `newTag` to the `images:` block of `k8s/envs/vagrant/kustomization.yaml` directly on `main`, touching only that file. A repository ruleset lets the GitHub Actions bot bypass the `ci-gate` requirement for this commit; the workflow ignores that path so it cannot trigger itself.
- **Argo CD:** installed by Ansible from its pinned official Helm chart (ADR 0003), minimal: Dex, notifications and the ApplicationSet controller disabled. One `Application` watches `k8s/envs/vagrant`. No app-of-apps.
- **Scope boundary:** Argo owns the app layer only: `api`, `web`, their routes, the migration Job, the smoke Job. Ansible and scripts own the rest: platform charts (Cilium, CNPG operator, Argo CD itself), the `pg` Cluster and its `fresh`/`restore` overlays (ADR 0011), and Secrets (`apply-secrets`, ADR 0015).
- **Repo access:** a read-only **deploy key** for this repo. Generated by `dev.yml` into `~/.config/health-tracker/` (mode 600, outside the repo) like the other secrets; `apply-secrets` creates Argo's repository Secret from it. Registered on GitHub from Windows with `gh repo deploy-key add`, titled "health-tracker argocd".
- **Migrations:** a `PreSync` hook Job with a fixed name and `hook-delete-policy: BeforeHookCreation`, from the `api` image, using `db-owner` (ADR 0015). Argo waits for it; if it fails the sync stops and the old `api` keeps running. **Rule: migrations are expand-then-contract.** The old `api` runs against the new schema during a rollout, so add first and remove in a later deploy (consistent with the additive-only API, ADR 0006).
- **Smoke test:** a `PostSync` hook Job from the `api` image, running ADR 0014's smoke script against the in-cluster Service with `api-token` mounted. Failure shows the app as Degraded. There is no automatic rollback in v1: rollback is `git revert`, which redeploys the old SHA through the same path.
- **Bootstrap and ordering (amends ADR 0011):** the `Application` is created with **auto-sync off**. `rebuild-cluster` order: Ansible (cluster, platform, Argo) → `apply-secrets` → `restore-data` → auto-sync on → the app deploys itself. `restore-data` also **suspends** auto-sync before stopping `api` and **resumes** it at the end, so Argo cannot scale `api` back up mid-restore. First install is the same path with `-Fresh`.
- **Argo UI:** no Gateway route. `kubectl port-forward` on the dev VM bound to `0.0.0.0`, browsed at `http://192.168.56.20:<port>`. The login is `argocd-initial-admin-secret`, read by hand, never through Claude (ADR 0015 guardrail).
- **Acceptance for build tickets:** one change made end to end (PR → merge → image → bump commit → migration → rollout → smoke green) and one deliberate failure (a bad migration leaves the old `api` serving); one `rebuild-cluster` ends with the app deployed and smoke-tested with no manual step; confirm the package-visibility flip and the ruleset bypass work as described; check Argo CD's chart version and values at build.

## Considered Options

- **Push from a self-hosted runner on the dev VM.** Simpler and no Argo CD to learn. Rejected: a long-lived process holding kubeconfig, driven by GitHub events, and a merge while the VM is off is missed. Pull catches up on boot.
- **Private GHCR with a read-only PAT pull secret.** Rejected: the cosmetic secrecy of app code is not worth one more credential, its rotation and `imagePullSecrets` in every manifest. Images hold no secrets.
- **A registry on the dev VM or in the cluster.** Rejected: unreachable from GitHub-hosted runners (and a cluster registry dies with a rebuild).
- **Auto-opened bump PR.** Rejected: PRs created with `GITHUB_TOKEN` do not trigger workflows, so `ci-gate` never runs and the PR waits forever.
- **Argo CD Image Updater.** Rejected: another component with the same write-back permission to git.
- **Argo owning everything, including `pg`.** Rejected: self-heal would fight `restore-data`, and the `fresh`/`restore` choice must stay a visible, guarded branch in the script.
- **Migration Job with a unique name per release, or an `initContainer`.** Rejected: the first leaves old Jobs and shows as drift; the second runs per replica, races, and has no clean failure.
- **Smoke test by hand on the dev VM.** Rejected: easy to forget, and the token would have to be read there. In-cluster it is mounted directly.
- **Release tags for deploys.** Rejected: ceremony for one user and one environment; `ci-gate` is the quality bar.
- **PAT or public repo for Argo's read access.** Rejected: a PAT is account-wide and expires; the repo stays private.

## Consequences

- **Amends ADR 0011:** `restore-data` suspends and resumes Argo's auto-sync; `rebuild-cluster` ends with the app deployed by Argo.
- **Amends ADR 0015:** the deploy key joins the secret inventory (an Argo repository Secret, from `apply-secrets`); there is no image pull secret. A dev VM rebuild generates a new deploy key: register it on GitHub and delete the old one. The note that the smoke script reads the token only on the dev VM is superseded: it runs in-cluster.
- **Amends ADR 0014:** the smoke script becomes the `PostSync` hook, shipped in the `api` image; its drift stays covered by `ci-gate`'s `docker build`.
- **Amends ADR 0009:** the Argo CD CLI is optional; add it to `dev.yml` only if the UI and `kubectl` prove insufficient.
- Bot commits land on `main` between your own, so pull before pushing. The ruleset bypass is a deliberate hole limited to one actor and, by workflow design, one file.
- Argo's controller and repo server cost memory on 4 GB workers even when trimmed; watch for pressure at build.
- If the PC is off during a merge, the image exists and the commit is on `main`; the deploy happens when the cluster comes up.
- v2: the same flow works against a cloud cluster; the registry stays, only the overlay and `iac/terraform/` change.
