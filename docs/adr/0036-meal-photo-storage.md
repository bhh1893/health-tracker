# Meal Photo bytes live in a Garage bucket on the dev VM, written synchronously

Meal Photo bytes live in their own `meal-photos` bucket in the existing Garage on the dev VM (ADR 0011), reached through the S3 API with a key scoped to that bucket. Postgres holds only each photo's key and metadata. An upload succeeds only after Garage has stored the bytes, and the client shows a photo only after that success. Decided in [Where Meal Photo bytes live](https://github.com/bhh1893/health-tracker/issues/296), on the map [Health Tracker v1: Meal Photos](https://github.com/bhh1893/health-tracker/issues/292). It amends ADR 0009 and ADR 0011.

## Shape

- **Survives a rebuild.** ADR 0005's rule covers photos: node disks are never trusted, so photo bytes live off the three node VMs, and `rebuild-cluster.ps1` leaves every photo in place.
- **Bucket:** `meal-photos`, on the same Garage instance as `backups`, with a Garage bucket quota as a store-side cap on total size. The numbers are set by [Meal Photo limits, quotas and threat model](https://github.com/bhh1893/health-tracker/issues/300).
- **Key separation:** `api` gets its own Garage key with read and write on `meal-photos` only. It cannot read or delete `backups`, and `cnpg-backup` has no access to `meal-photos`. Like `cnpg-backup`, the key is generated by `dev.yml` and reaches the cluster through `apply-secrets` (ADR 0015).
- **Synchronous write, no queue.** "Visible means saved": `api` answers success only once Garage has the bytes. A failed or dropped upload shows on the client as a failed photo (✕ with retry) and is never shown as saved. Anything not acknowledged may be lost.
- **Recovery promise:** after acknowledgement, a photo is one copy in Garage until the next copy leaves the dev VM. Losing the dev VM's disk loses photos since that copy. This promise is weaker than the one for Meals (about one minute of WAL). How the copy is made and how often is settled in [Backing up and restoring Meal Photos](https://github.com/bhh1893/health-tracker/issues/301).
- **Degradation:** with the dev VM halted, photo upload and viewing fail while Meals keep working. The client shows a placeholder for a photo it cannot load. A photo outage never blocks logging a Meal.
- **Portability contract is the S3 API.** Service code speaks only the S3 protocol, with endpoint, bucket and keys from env vars. That runs unchanged on Garage, AWS S3, Cloudflare R2 and GCS (XML API). Azure Blob needs a gateway (S3Proxy) in IaC. **"Provider SDK"** (`CLAUDE.md`) means a library bound to one vendor's own API. An S3 client pointed at a configurable endpoint is not one. The library itself is chosen in [Upload and download path for Meal Photos](https://github.com/bhh1893/health-tracker/issues/297).
- **No encryption at rest in v1.** Garage stores the files unencrypted on the dev VM's disk, as it already does the database backups. Every cloud target encrypts by default, so a move to one closes this. The threat-model ticket records the exposure.

## Considered Options

- **Postgres `bytea`.** One store, deletes in the same transaction, backed up by the existing WAL archive. Rejected: `pg`'s 5 Gi local-path volume cannot grow without a restore, and every byte is paid for twice (replica), again in WAL and again in every base backup. Restore time (about 90 s today) grows with it, and sign-up is open (ADR 0026), so strangers' photos would share that disk.
- **A volume shared by `api` pods.** Rejected: a node disk, so a rebuild destroys it, and it is not portable.
- **An object store in the cluster.** Rejected for the same reason ADR 0011 gave for backups: a rebuild destroys it.
- **A queue (Kafka) between upload and storage, on its own pod.** Rejected: "visible means saved" requires the bytes to be durable before success, so the queue would have to be durable storage itself. That makes a third stateful system to run, size and back up on 4 GB workers, and Kafka's 1 MB default message cap is not built for files. Async processing after the bytes are safe is still open to [Processing a Meal Photo](https://github.com/bhh1893/health-tracker/issues/298).
- **A 5th VM as the photo store.** Rejected: it would share the PC's disk with the dev VM, so it adds RAM cost but no durability. The dev VM is already outside the cluster.
- **A second Garage instance for photos.** Rejected: same disk, so it isolates nothing that scoped keys and a quota do not already isolate.
- **SSE-C on Garage.** Rejected: the service would hold the encryption key, and AWS disables SSE-C by default on new buckets since April 2026, so it is not portable.

## Consequences

- **Amends ADR 0009:** the dev VM now holds unique user data (Meal Photos), not just backups and secrets, and it sits in the request path for photos. `vagrant destroy` on it loses every photo since the last copy off it, so the runbook warning grows to say so.
- **Amends ADR 0011:** Garage serves two buckets with two scoped keys. The `backups` bucket and the `cnpg-backup` key are unchanged.
- Postgres and Garage must be kept consistent (orphan bytes, deletes, a Meal deleted mid-upload). That is the job of [Meal Photo data model, API and deletes](https://github.com/bhh1893/health-tracker/issues/299).
- Garage listens on plain HTTP on the host-only network, so phones cannot reach it. A browser-direct (presigned URL) path would need it exposed through the edge. [Upload and download path for Meal Photos](https://github.com/bhh1893/health-tracker/issues/297) weighs that against proxying through `api`.
- Moving clouds swaps the endpoint and the keys, and the existing photos have to be copied across. That copy is still in the map's fog.
